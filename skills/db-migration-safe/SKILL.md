# Db Migration Safe

## When to use
A schema change will run against a database the application is using.

## Steps
1. Identify engine and version, table sizes, write traffic and how deploys order migrations and code. Lock behaviour depends on all of these; check the engine's documentation for the exact statement.
2. Read the SQL the migration tool will emit, not only the model change. Autogenerated renames often become drop plus add.
3. Check compatibility both ways: the old code must run on the new schema and a code rollback must still work.
4. Split incompatible changes: add the new form, write both, backfill, switch reads, stop old writes, and drop in a later release.
5. Keep large data updates out of the schema transaction; batch them as a separate resumable job.
6. On PostgreSQL, set a short `lock_timeout` and retry; build indexes with `CREATE INDEX CONCURRENTLY` outside a transaction and check for an invalid index after failure; add foreign key and check constraints `NOT VALID`, then `VALIDATE CONSTRAINT`.
7. Rehearse on a production-sized synthetic or approved copy. Time each statement and watch which locks it takes.
8. Write the recovery: a tested down step, or a forward fix where data would be lost. Confirm a restorable backup before destructive steps.
9. Add verification queries and abort criteria. Running against production needs the user's approval.

## Watch out for
- A quick `ALTER` waiting behind a long transaction can queue every later query behind it.
- A down migration that recreates a dropped column does not restore its data.
- "No code references it" is wrong if old instances, reports or jobs still read the column.
- Test databases with ten rows prove only syntax.

## Operating rules
- Look before you change anything: read the real files, data or page first.
- Report what you actually ran and saw; never invent results, sources or numbers.
- Ask before destructive, paid, public or irreversible actions.
- Never print, store or commit secrets or private personal data.

## Done when
The emitted SQL is reviewed, each step states its lock and compatibility effect, it ran on a rehearsal copy with timings, and recovery steps are written.
