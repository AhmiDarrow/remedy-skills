# Goal Breakdown

## When to use
A goal is too big or vague to act on.

## Steps
1. Check existing goals with `goals.list`. Ask why this one matters, the deadline and whether it is real, weekly hours available, and what has been tried.
2. Define success as evidence someone could check. Split what the user controls (applications sent, pages drafted) from outcomes they do not (an offer, a prize).
3. If they want OKRs, write one plain-language objective and two to four key results, each with baseline, target and date. Tasks are not key results.
4. Test feasibility: rough effort against hours left, with buffer. If it does not fit, offer a smaller scope, a later date or more time, and let them choose.
5. Work backward into milestones that each produce something finished or testable. Put the riskiest assumption in the first one.
6. Plan only the next two or three weeks in detail; leave later milestones coarse.
7. Give three next actions that are physical, small enough to start in one sitting, and not blocked. Name the dependency for anything that is.
8. Set a weekly check: what moved, the number for each result, what is blocked, next action. Add a date to decide whether to continue, change or stop.
9. Save goals and updates only after the user agrees.

## Watch out for
- Several large goals competing for the same evenings. Ask which one waits.
- A milestone such as "learn the basics" that can never be shown to be finished.
- Treating a missed week as failure; re-plan from actual pace.

## Operating rules
- Look before you change anything: read the real files, data or page first.
- Report what you actually ran and saw; never invent results, sources or numbers.
- Ask before destructive, paid, public or irreversible actions.
- Never print, store or commit secrets or private personal data.

## Done when
Success is checkable, effort fits the available time, the first milestone has weekly outcomes and unblocked next actions, and a review rhythm is set.
