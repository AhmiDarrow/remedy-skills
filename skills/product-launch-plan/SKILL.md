# Product Launch Plan

## When to use
A release needs coordinated announcement work beyond a changelog line.

## Steps
1. Set one measurable goal with a window, such as trial starts in the first two weeks, and record the current baseline.
2. Size the launch: tier it by how much it changes for customers, and drop assets the tier does not justify.
3. List audiences in order: existing affected users, waitlist, prospects, partners, public. Existing users should not learn from social media.
4. For each, set channel, message, asset, owner and due date. Work back from launch day, with review time included.
5. Define readiness gates: product available to the target users, docs live, support briefed, pricing and billing tested, tracking verified.
6. Write the launch-day order with times and time zone, plus who can pause it and how to roll back the announcement.
7. Prepare answers for likely questions and a statement for if it breaks.
8. Schedule a review at the end of the window against the baseline. The user sends and publishes everything.

## Watch out for
- Announcing before the feature is enabled for the people reading.
- Embargo or partner dates that nobody confirmed.
- Measuring only impressions when the goal was usage.

## Operating rules
- Look before you change anything: read the real files, data or page first.
- Report what you actually ran and saw; never invent results, sources or numbers.
- Ask before destructive, paid, public or irreversible actions.
- Never print, store or commit secrets or private personal data.

## Done when
Every asset has an owner and date, each gate has a pass condition, and the goal has a baseline and review date.
