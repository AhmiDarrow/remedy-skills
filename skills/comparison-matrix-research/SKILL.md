# Comparison Matrix Research

## When to use
Three or more candidates need to be compared on criteria that matter to this user.

## Steps
1. Get the use case and separate must-have criteria from preferences. Define each so it has a testable answer: "exports all data as CSV or JSON", not "good export".
2. List candidates, including doing nothing or keeping the current setup. Record why any obvious one is left out.
3. Eliminate on must-haves first, so deep research is spent only on survivors.
4. Fill the table criterion by criterion across all options, using the same source type for each: official documentation, then independent testing, then user reports.
5. Each cell gets a value, a source link and the date checked. Use "not documented" when silent; do not infer "no".
6. Normalise units and plan tiers so prices and limits describe the same quantity of use.
7. Mark vendor claims you could not independently confirm.
8. Recommend in terms of the user's priorities and name the fact that would change the recommendation.

## Watch out for
- Comparison articles are often affiliate-funded and out of date. Use them to find candidates, not to fill cells.
- A weighted score hides judgement behind arithmetic. If you use weights, show them and test whether a modest change flips the winner.
- A checkbox feature may exist only on a higher tier, one platform or in beta.
- Blank cells read as parity. Fill them or label them.

## Operating rules
- Look before you change anything: read the real files, data or page first.
- Report what you actually ran and saw; never invent results, sources or numbers.
- Ask before destructive, paid, public or irreversible actions.
- Never print, store or commit secrets or private personal data.

## Done when
Every surviving option has every criterion filled or labelled not documented, with sources, and the recommendation names its deciding factor.
